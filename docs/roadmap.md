# 产品 roadmap

**exocortex 要成为两样对外有价值的东西：一个 agent 自己维护、别人拿走就能用的研究 wiki；一个公开的 agentic robotics 追踪页。两者的前提相同：默认无人值守，human 只定方向、只撤销。** 现在离这个前提最远，所以先做它。

设计理由与已知缺口见 [design.md](design.md)。下文的数字目标是起点，由 human 定稿。

## 现在还不是 agentic-ready

每一次收录都要 human 在对话里开口，几处判断仍等人。

| human 现在要做的 | 目标 |
|---|---|
| 说「收录 inbox」「feed 收录」才会收录 | 每天定时无头运行，开 PR，收录类 PR 照旧自动合并 |
| 批准 / 并入 / 否决每个候选 lens | agent 直接建，human 撤销；这会改掉 design.md 里唯一的事前人工门，先看 agent 建的 lens 被撤销的比例 |
| 逐条处置搜索候选 | 过质量门的直接收录，human 撤销；门比 feed 严，因为搜索结果没有人的动作背书 |
| 核对 LLM 写的数字（实际没人做） | 收录后由另一个 agent 抽查关键数字是否与原文一致，不一致的退回重写 |
| feed 的浏览器 cookie 过期后手动更换 | 默认改用不需要 cookie 的官方接口，见下文「feed 的来源」 |
| 维护运行 feed 的私有机器与 cron | 换到任何能跑定时任务的地方（如 GitHub Actions），私有数据仍不进仓库 |

代码、规则、workflow 的改动仍由 human 合并，这一项不变。

## 产品一：agent 维护的研究 wiki

**用户**：想让 agent 替自己长期维护某个研究方向资料的独立开发者或研究者。

**定位**：NotebookLM、Zotero 加 AI 插件这类工具帮你读你收集好的文档；exocortex 替你收集，并持续维护一个方向的现状：有哪些工作、在什么评测上报了多少、是自报还是第三方复评、彼此怎么关联，存成你自己拥有的 markdown 与 git 历史。

- **规则与内容分开**：引擎（`AGENTS.md`、`scripts/`、`feed/`）与内容（`wiki/`、`inbox/`）拆开，用的人拿到的是空库，不用先删别人的 48 个来源。
- **规则短到能被照做**：去重、校验、合并这类不需要判断的步骤全部下沉进脚本，`AGENTS.md` 只留需要判断的部分，从 159 行压到 80 行以内；英文。
- **不依赖私有机器的上手路径**：定时任务、key 放在仓库 secrets，一条命令跑一次收录；不绑定 Cursor，Claude Code、Codex CLI 等无头 agent 都能跑。
- **每条收录的 token 开销可见**，用的人能判断值不值。

### feed 的来源

feed 是和普通 RSS 订阅拉开差距的那部分，而它现在依赖浏览器 cookie 读 GitHub 的非公开接口：别人复制不了，也处在服务条款的灰色地带。

- **默认**：改用官方 API（用 token 取关注者的公开事件），不需要 cookie，可以放进定时任务。代价是延迟与漏项：逐人拉事件的一次实测里，16 对「关注者 → 仓库」命中 14 对，漏掉的 2 对都是新建仓库。
- **可选**：cookie 读 feed 留作自托管用户的高级选项，不进默认上手路径。
- **决定依据**：同一天两种来源并排跑，官方 API 覆盖 feed 的 90% 以上就切为默认；不到就保留 cookie 为默认，并在文档里写明风险。

**验收**：一个陌生人只看 README，从零跑出第一份自动合并的收录 PR，两周后定时任务仍开着。

## 产品二：公开的 agentic robotics 追踪页

**用户**：做或关注 agentic robotics 的研究者，想知道这个方向最近出了什么、哪些值得看、数字可不可信。

- **覆盖**：按 lens 搜新工作作为第三个源（质量门见上表）；同一工作的仓库、论文、项目页归成一条。目标是追踪页的每个 lens 近 90 天至少 30 个工作，一半以上的工作至少有一条库内关联（现在最大的 lens 17 个、全库关联 9 条）。
- **更新**：每天自动；页面显示每条的日期与本周新增，提供 RSS。
- **英文页面**。
- **可信度**：保留自报 / 第三方标注；抽查 agent 的结果公开；读者能用一个 issue 指出错数字。抽查的数字错误率低于 2% 才对外发布。

### 策展判断：口味与事实分开

个人策展的价值在口味，而现在的规则让总结中立、不排高下，口味没有出现在页面上。

- **展示什么**：每个 lens 加一节「策展判断」，回答哪几个工作值得看、为什么、证据有多硬（第三方复评、评测是否饱和、是否开源）。中立规则只管每条工作的事实行与总结。
- **谁来写**：agent 写，依据是从 human 行为里学到的偏好（`prefer(work)`）与来源页里的证据；human 只纠正，纠正也成为偏好的标签。
- **现有判定理由不能直接用**：它写的是「像哪个标过的工作或 star」，说明的是相似，不是重要性；判定要改为同时说明这个工作重要在哪。

**验收**：上线 8 周内出现以下任一外部信号：50 个 star、20 个 RSS 订阅、3 个读者提的纠错 issue。都没有就重新评估这个产品。

## 顺序

1. **无人值守**：定时无头收录、抽查 agent、token 计量、feed 来源的决定。两个产品都卡在这一步。
2. **追踪页**：英文、日期与本周新增、RSS、lens 搜索、策展判断。内容先有人看，才知道引擎值不值得被复用。
3. **引擎模板化**：流程稳定后再把规则与内容拆开、压短 `AGENTS.md`、写上手路径，避免拆完又改。

## 衡量

| 指标 | 目标 |
|---|---|
| human 每周介入次数 | 只剩「删 X」、纠正策展判断与改 lens 范围句 |
| 撤销比例 | 收录后被「删 X」的比例，看趋势，不设门 |
| 抽查错误率 | 对外发布前 < 2% |
| 追踪页覆盖 | 每个 lens 近 90 天 ≥ 30 个工作，≥ 50% 有库内关联 |
| 每天 token | 判定与收录分开记 |
| 外部信号 | 追踪页上线 8 周内：50 star、20 订阅或 3 个纠错 issue 之一 |

## 不做

- 托管服务、多用户账号。
- 覆盖所有领域的通用论文推荐；追踪页只做 agentic robotics。
- 重新引入逐条人工预审。
